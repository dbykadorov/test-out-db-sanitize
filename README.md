# Сервис обезличивания баз данных

Копия боевой базы для разработки и аналитики, из которой убраны персональные
данные - так, чтобы приложение по-прежнему работало, отчёты сходились,
а восстановить исходные значения было нельзя.

## Как запустить

```bash
cd stand
docker compose up -d
```

Первый запуск занимает несколько минут: собираются образы и поднимается
детектор персональных данных - он грузит модели spaCy и до готовности
не отвечает. Дождаться готовности:

```bash
docker compose ps
```

Посмотреть, что вообще можно заказать:

```bash
curl -s http://127.0.0.1:8080/api/sources | jq .
```

Заказать выгрузку:

```bash
curl -X POST http://127.0.0.1:8080/api/requests \
  -H 'Content-Type: application/json' \
  -H 'X-Subject: owner@outtech.example' \
  -d '{"purpose":"Копия для разработки","sourceId":"demo-prod","sinkId":"demo-sanitary"}'
```

**Строку подключения в заявке передать нельзя.** Заявка называет источник
идентификатором из реестра контура; учётные данные к нему воркер берёт сам,
из каталога в плоскости данных. Иначе контур управления начал бы носить
учётные данные - а по разделу 2 архитектуры доступа к данным у него нет
вовсе, - и любая заявка превращала бы воркер в утилиту «подключись куда
скажут» от его имени.

## Как подключить свою базу или свой дамп

Одна строка в `stand/.env` - и всё. Шаблон есть в `stand/.env.example`,
каталог контура на эти переменные уже ссылается.

**Своя база:**

```bash
cd stand
echo 'MY_SOURCE_DSN=Host=192.168.1.10;Port=5432;Username=readonly;Password=секрет;Database=prod' >> .env
docker compose up -d worker
```

Через пятнадцать секунд она появится в `GET /api/sources` как `my-source`.
Учётная запись нужна только на чтение: в источник прогон не пишет.

**Свой дамп:** положить файл в `stand/inbox/` и назвать его:

```bash
cp ~/prod.dump inbox/
echo 'MY_DUMP_FILE=prod.dump' >> .env
docker compose up -d worker
```

Появится как `my-dump`. Форматы: `pg_dump -Fc`, каталог `-Fd`, обычный
текстовый `.sql`; формат определяется по содержимому файла, а не по расширению.
Дамп разворачивается в промежуточную базу рабочей зоны, и дальше идёт ровно
тот же конвейер - иначе стадии анализа не по чему считать агрегаты и выборки.
Промежуточная база стирается перед каждой загрузкой: остатки предыдущего
прогона - это чужие персональные данные.

**Свой приёмник:** `MY_SINK_DSN`, появится как `my-sink`. Эта база
**перезаписывается** прогоном: схема в ней удаляется и создаётся заново.

Затем обычная заявка:

```bash
curl -X POST http://127.0.0.1:8080/api/requests \
  -H 'Content-Type: application/json' -H 'X-Subject: owner@outtech.example' \
  -d '{"purpose":"Своя база","sourceId":"my-source","sinkId":"demo-sanitary"}'
```

### Почему именно так, а не полем в заявке

Учётные данные не проходят через контур управления - иначе они осели бы
в таблице заявок, в аудите и в логах API, а раздел 2 архитектуры утверждает,
что доступа к данным у него нет вовсе. Заодно это закрывает очевидное
злоупотребление: заявка со строкой подключения превращала бы воркер
в утилиту «подключись куда скажут» от его имени.

Поэтому подключения живут в каталоге плоскости данных
(`stand/config/catalog.json`, ссылается на переменные окружения), а в контур
управления воркер сам сообщает только имя, заголовок и вид. Файл `.env`
в репозиторий не попадает.

Незаданная переменная не подставляется пустотой: запись каталога пропускается,
и воркер называет её в журнале - `источник каталога пропущен - my-source:
переменная MY_SOURCE_DSN не задана`. Шаблон в каталоге не ломает уже
работающие источники, а опечатка в имени переменной не выглядит как
«источник почему-то не появился».

Признак `ready` в `GET /api/sources` показывает, объявил ли воркер ресурс
своим. Заявка на неготовый ресурс отклоняется сразу, а не падает в середине
прогона.

## Что это делает

Прогон состоит из четырёх стадий.

**Анализ.** Интроспекция схемы, выборка значений, разметка колонок. Решение
собирается из четырёх независимых признаков: имя колонки, комментарий к объекту
схемы, форма значений с контрольными суммами, разбор свободного текста
детектором. Всё, что ниже порога уверенности, уходит человеку на утверждение,
и без его решения прогон не начинается. Правило разрешения споров -
«неизвестно значит чувствительно».

**План.** Из утверждённой политики строится план: какие домены нужны, где
требуется биекция, где достаточно чистой функции, где домен ограничен схемой
и нужна перестановка без неподвижных точек.

**Исполнение.** Перенос выполняет Greenmask - дамп с трансформацией на лету
и восстановление. Наш процесс подключается к нему через трансформер `Cmd`
и отвечает за то, чего Greenmask не умеет: единственность замены, биекцию,
конечные домены, персональные данные внутри документов.

**Проверка.** Прогон не считается успешным, пока не пройдены проверки
требований. Провал блокирующей проверки означает, что артефакт **не публикуется
вовсе**: частично обезличенная база опаснее отсутствующей.

Каждый артефакт сопровождает паспорт выгрузки - машиночитаемый документ
с перечнем заменённых и **незаменённых** колонок с причинами, результатами всех
проверок, принятыми остаточными рисками и именованными отступлениями.

## Как это устроено

| Слой | Что делает |
|---|---|
| `src/Sanitize.Core` | ядро замен: канонизация, PRF, генераторы, словарь, беспорядок, модель политики. Ни строчки SQL и ни одного клиента внешнего сервиса - это проверяется тестом на графе зависимостей и на лексике исходников |
| `src/Sanitize.Adapters.Postgres` | всё знание о PostgreSQL: интроспекция, агрегаты, конфигурация и запуск Greenmask |
| `src/Sanitize.Transformer` | процесс канала `Cmd`: разбор потока, пул обработчиков, буфер переупорядочения |
| `src/Sanitize.Dictionary` | словарь прогона на диске, отображение в память |
| `src/Sanitize.Detection.Presidio` | разбор свободного текста |
| `src/Sanitize.Worker` | четыре стадии, проверки, паспорт |
| `src/Sanitize.Service` | API заявок, роли, аудит - контур управления |
| `src/Sanitize.Delivery` | выдача артефакта: аутентификация получателя, отзыв, аудит |

Решения и их цена описаны там, где они приняты - в комментариях к коду,
а не в отдельном документе: комментарий рядом с кодом не расходится с ним
при правке, а документ расходится.

## Ограничения данной версии

Хранилище секретов и провайдер идентичности заменены заглушками: секрет
замены подаётся файлом только на чтение, идентичность проверяется
по статическому списку - теряются ротация секрета, временные учётные данные
и проверка подписи токена, сохраняются разграничение ролей, привязка выдачи
к заявке, отзыв и аудит. Обобщение квази-идентификаторов не делается вовсе:
сочетание незаменённых колонок может выделять человека, и этот риск принят
и записан в паспорт, а не закрыт. Свободный текст не обрабатывается точечно -
текстовые колонки по умолчанию затираются целиком, потому что полнота
обнаружения персональных данных в тексте не равна ста процентам ни при каком
пороге, и плата за это названа: содержание текста для аналитики теряется.
Объём стенд не показывает - демо-база это тысячи строк против миллиардов
в нормативном объёме задания, замеры на 0,1 / 1 / 10 ГБ не снимались,
и утверждение об узком месте (разбор естественного языка) остаётся расчётом,
а не измерением. Наконец, словарь замен строится в памяти воркера: на 200 млн
различных чувствительных значений это не сработает - понадобится строить его
множественной операцией в отдельной базе рабочей зоны и переносить готовым
томом; механизм чтения словаря на такой объём рассчитан, а построение нет,
и это названный разрыв, а не решённая задача.

## Секрет замены на стенде

Файл `stand/secrets/run-secret` содержит **демонстрационное** значение
и лежит в репозитории намеренно, чтобы стенд поднимался одной командой.
В боевом контуре на его месте хранилище секретов; заглушка соблюдает оба
правила настоящего: секрет подаётся файлом только на чтение и не попадает
ни в переменные окружения, ни в аргументы запуска процесса.

Смена секрета меняет все замены. Повторяемость выгрузок между прогонами
обеспечивается не повтором секрета, а режимом переноса словаря - это
отдельное явное ослабление, и оно попадает в паспорт.
